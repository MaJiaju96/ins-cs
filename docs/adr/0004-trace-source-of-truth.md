# ADR-0004 trace 落 MariaDB，可观测平台只做旁路

- 状态：已采纳
- 日期：2026-10-30
- 相关：`TraceSink`、`span`/`turn` 表、Langfuse 接入（P1-9）

## 背景

参照系统的做法是把 trace 交给外部可观测平台，仓库里不落库（执行上下文只存在内存，
没有状态快照表，进程重启不可恢复）。这对「看单条链路」是够的。

但我们需要的查询形态是分析型：

- 上周降级率是多少？哪个域最高？
- 改完这条规则，命中率/误问率变了吗？
- 这一轮和三个月前那一轮，差别在哪？
- 某条 `rule_id` 的平均耗时、P95、失败率

这些需要 `GROUP BY`、join、窗口函数，且**不能接受采样丢一半**。

## 决策

1. **MariaDB 的 `turn` + `span` 是唯一事实源。** 一轮 = 1 行 turn + N 行 span。
2. **外部可观测平台（Langfuse）只做旁路导出**：异步、允许丢、失败只记日志。
3. 落库是**批量一次**（turn + spans 一起），不逐 span 往返。写失败只记日志，不影响用户回复。
4. 降级路径必须留 span（`status=DEGRADED`），否则视为 bug——降级不可见的系统会悄悄烂掉。

## 后果

- 好：能做自助分析；能回放与 diff；对一个「要证明自己是对的」的项目，这是核心资产。
- 坏：多一次写（异步）；表会持续增长（按 `created_at` 分区/归档，已预留索引）。
- 约束：`span.attributes` 用 JSON 列而不拆字段——属性会一直长；拆成列等于逼自己每次改表。
- 不做的：不做分布式追踪的完整语义（跨进程 context 传播），单机单进程不需要。

# ADR-0003 分流规则的事实源在仓库，不在配置中心

- 状态：已采纳
- 日期：2026-10-30
- 相关：`RouteRule`、`route_rule` 表、`docs/design-notes/reference-system.md` 第三节

## 背景

参考系统把 Agent 树、路由条件、prompt、模型、候选 SKU 全部放在动态配置中心，运营可以不重启热改。
那是多人协作场景下的合理取舍。

但它支付了一个真实代价：**「线上为什么这么分流」在仓库里查不到，也测不了。**
仓库只能说明「消费逻辑」，说明不了「当前生效的值」。对一个只有自己维护、且要靠它证明能力的项目，这个代价不可接受。

## 决策

线划在这里：

- **结构与规则进仓库**：`route_rule` 的内容通过 Flyway 迁移文件变更，走 code review 与 CI。
- **参数与开关进配置中心**：阈值（0.8/0.3）、模型选择、超时、功能开关可以热改。
- 规则加载走 `RouteRuleProvider`（DB + 60s 缓存），实现可替换，但**数据来源必须是可 diff 的**。

## 后果

- 好：任何一条规则的来历都能 `git log` 出来；规则集可被单测覆盖（测试直接构造 `List<RouteRule>`）。
- 坏：改一条规则要走一次发布，比热改慢。**这是有意的**：分流逻辑的高频热改通常是坏味道。
- 约束：规则 id 不改（写进 trace，是契约）；下线规则用 `enabled=0` 而不是删行。
- 反例守卫：如果将来真的需要运营热改，做法是「运营在配置台改草稿 → 生成迁移 → 发布」，而不是让线上直接生效（见 roadmap P2-4）。

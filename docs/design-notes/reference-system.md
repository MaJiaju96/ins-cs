# 参考系统拆解：哪些巧思值得学，哪些是负债

> 本文是对一套**线上生产级 AI 客服系统**架构的匿名化拆解。原文材料只在本地参考、不进仓库；
> 这里不保留任何内部系统名、包名、表名与业务标识。结论只对「我们」的处境负责。

那套系统是多年长出来的：8 个 Maven 模块、7 种目标 Agent 类型（本地编排框架 / 远程 Agent 平台 / A2A / 各类 RPC / 静态数据）、
三套条件表达式引擎、动态配置驱动的 Agent 树、外部记忆服务、外部知识平台。我们能看到的只有静态结构，
但足够回答一个问题：**哪些设计是被约束逼出来的（值得学），哪些是被组织规模逼出来的（我们抄了就是负债）。**

## 一、五个真正的巧思

### 1. 先造「信封」，再谈框架

它最值钱的不是那套 Agent 编排，而是 `Bridge<T,E>`：一个统一签名把「任意来源的请求」变成「任意目标 Agent 的执行」，
内部契约把 N×M 的适配矩阵压成了 N+M。

**但我们不需要它的注册表工厂。** 它需要 `TypedTargetBridgeFactory` 是因为有 7 种目标类型；
我们只有「本地 Bean」一种，抽象没有第二个实现来验证，写了就是空转。

我们只保留「信封」这件事本身：`TurnResult` 就是我们的信封——拿到它，评测台就能判断一轮对不对、贵不贵、慢不慢。

**顺便修正一个判断标准**：它设计 IR 的问题意识是「前端要渲染什么」。我们的 IR 有第二个消费者（评测台），
所以字段标准应该更严：**一年后看这条记录，能不能判断这一轮对错？** 不能的字段就别加。

### 2. 「传什么」与「记什么」必须拆成两个对象

它有两个上下文：`AgentContext`（可序列化、跨 Agent 传递的业务与会话上下文）和 `RunContext`（单次运行的父子树：
组件、观测、耗时、首 token、错误、中断标记）。这个拆分是对的，而且比大多数人做得干净。

我们据此把 IR 从「按信息丰富度分 L0/L1/L2」改成**按角色分三层**：

| 层 | 类型 | 生命周期 | 事实源 |
| --- | --- | --- | --- |
| 知道 | `TurnContext` | 单轮输入 | `turn` 表 |
| 做了 | `RunTrace`/`Span` | 单轮执行 | `span` 表 |
| 说了 | `Block`/`TurnResult` | 单轮输出 | `turn.blocks_json` |

理由是：三层信息量接近，但生命周期与事实源完全不同。混在一起会导致「重放时分不清哪些是输入、哪些是过程」。

### 3. 允许调用方直接给意图

它有一个白名单：上游系统可以直接把意图传进来，跳过 LLM 识别。这是**把确定性留在确定性层**的典型手法——
已经有答案的地方，不要再问一次模型。

我们把它扩大成「分流四态」：`HIT_RULE`（规则命中，0 次模型调用）/ `HIT_MODEL`（模型兜底）/ `ASK_BACK`（反问）/
`DEGRADED`（命中但域不可用）。**关键是四态必须落库**——它没做到这点，所以「路由命中率」「误问率」在它那里是不可测的。

### 4. 检索的中间态，动作是「问」不是「答」

它的向量检索用三档：`>=0.8` 直接用，`0.3~0.8` 转成「编号候选澄清问题」，`<0.3` 跳过。
这个阈值三分法看着朴素，但它做对了一件很少有人做对的事：**中间不确定性不让模型去补**，而是变成一次交互。

我们照抄这个思路（阈值可配置，默认 0.8/0.3），并延伸一步：用户回「2」走 `EXACT` 规则，
确定性分支，**不再过一次模型**。一次反问换来的是后面整条链路的确定性。

### 5. 降级链的每一级都在换假设，而不是重试

产品推荐的 10 步里，从「LLM 抽条件定位」到「只用产品名重召回」，到「读配置候选 SKU」，到「过滤无法生成链接的」——
每一级都在换一个假设，而不是同一个调用再试一遍。另外它给每个 Bridge 节点配了 `errOut`：
**每个域自带降级话术**，而不是全局一句「系统繁忙」。

这条我们直接采纳，并且写进了代码约定：

- `retry`（同假设重复）在 2 Mbps 上就是放大器——一次 60ms 变成 180ms，还可能是三倍无效流量；
- `fallback`（换假设）才能真的把用户送到出口；
- 话术键跟着规则走（`route_rule.fallback_msg_key`），所以「退保查不到」和「理赔查不到」说的是两句不同的话。

## 二、三条可迁移的原则

1. **不确定性是合法状态，不是异常。** 它用「兜底澄清意图」而不是抛错，这是对的方向；但它同时把模型异常 sleep 100ms 重试一次，那是错的补偿方式。
2. **降级要换假设，不要重试。** 见巧思 5。
3. **上下文前置换掉往返。** 入口一次查全（订单/保单/用户），下游只读不回查。它做的是「上游传 history，Memory 再查一遍然后合并」——那等于把往返翻倍，还引入了「两个来源不一致」的问题。

## 三、明确不抄的

| 不抄 | 它的理由（对它是合理的） | 我们的情况 |
| --- | --- | --- |
| 8 模块拆分（common/domain/dao/rpc/service/facade/web） | 多人协作、分层治理、RPC 边界 | 一个人 + 一个前端，拆越细只增加跳转成本 |
| Agent 编排框架 + 7 种目标类型注册表 | 多团队接入 | 只有本地 Bean，等第二种目标真出现再抽象 |
| 三套条件表达式（MVEL/JsonPath/JSONata） | 不重启改 Agent 树 | 一个人维护三套 DSL 是纯负债；复杂条件写实现类 |
| 动态配置驱动全部行为（含路由与 prompt） | 运营同学要能热改 | **代价是「线上为什么这么分流」在仓库里查不到，也测不了** → 见 ADR-0003 |
| 外部记忆服务（含 sessionId=sha256(pin) 的隔离设计） | 记忆被多个系统共享 | 记忆就是 `turn` 表 + 一次最近 N 轮查询 |
| 连接池 200 | 高并发 | 弱网 + 单机，5–10 就够；开大只会把弱网放大成雪崩 |
| SSE 超时 120s | 长任务 | 单轮 P95 < 2s 是目标，超时应该早失败 |
| 赠品绑定那套缓存/预热/唯一键 | 真实业务 | 与本项目无关 |

## 四、它的 22 个原生局限里，值得当反面教材的几条

- **执行上下文不持久化**（内存里的树 / 任务对象），进程重启即不可恢复 → 我们落 `turn`+`span`。
- **双执行路径**：新入口走新链路，状态查询接口还打旧服务。→ 我们一个入口、一个事实源。
- **历史合并多源不按时间排序**，只按 msgId 去重后截尾 → 我们只认 `seq`。
- **写入重试无退避**（立即重试 3 次）→ 我们退避 + 幂等键。
- **部分失败仍返回成功**（知识同步单条失败累计后仍 `true`）→ 我们的落库失败要能被观测到（span=DEGRADED）。
- **仓库只能说明消费逻辑**：Agent 树、prompt、模型、候选 SKU 的真实值都在配置中心 → 这是我们最想避开的一种状态。

## 五、我们的差异化机会

它的 trace 不上库。这不是疏忽，是取舍：它把 trace 交给了外部可观测平台，而平台的模型（采样、按 span 查询、按会话浏览）
不支持「对上周 200 个会话做 GROUP BY」。于是它无法回答：

- 上周降级率是多少？哪个域最高？
- 改完这条规则，命中率变了吗？误问率变了吗？
- 这一轮和三个月前那一轮，差别在哪？

**我们落库、可回放、可 diff。** 这就是这个项目区别于「又一个客服 demo」的地方——
不是功能更多，是**能证明自己是对的**。

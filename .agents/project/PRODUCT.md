# PRODUCT.md — 目标、用户、范围

## 定位

一个**能长期长**的个人全栈项目：AI 保险客服机器人（`cs-bot`）+ 围绕它的评测与运营卫星（`cs-lab` 等）。

两个用途，缺一不可：

1. **能力证明**：证明能设计一个多层 Agent 客服系统，并且能证明它对不对（trace/回放/评测）。
2. **长期主线**：之后所有卫星系统（badcase 收集箱、轨迹回放、评测台、配置台、成本看板、话术质检）都长在它上面，不另起炉灶。

## 用户

| 用户 | 他要什么 | 我们这个项目给什么 |
| --- | --- | --- |
| 评审者（面试/同行） | 30 秒内看出「这人有工程判断，不只是会调 API」 | README 第一屏就是矛盾与解法；代码里有代价说明的注释；有一条能跑的命令 |
| 自己（维护者） | 三个月后还能改得动 | 规则进仓库、ADR 记录理由、`.agents/` 存上下文、trace 可回放 |
| 虚构投保人（演示） | 问退保/理赔时拿到准确答复，而不是「系统繁忙」 | 四态分流、带引用的回答、编号候选、转人工交接包 |

## 场景（P0 只做这五个）

1. 「订单 A1024 现在什么状态」→ 查库回订单卡片
2. 「我想退保」→ 条款摘要 + 退保试算入口 + 选项
3. 「理赔要什么材料」→ 材料清单 + 后续选项
4. 「转人工」→ 交接摘要包落待处理列表
5. 「你好呀」（无法判断）→ 反问 + 编号菜单，不猜

## 价值

- 对用户：不确定时给选项而不是编答案；要人时不让人等
- 对维护者：任何一轮都能回答「为什么这么答」——`turn.route_state` + `rule_id` + `span` 树
- 对项目本身：评测台不是附属品，是同一套 IR 的第二个消费者

## 范围外（明确不做）

- 真实业务接入、真实条款/保单、真实支付与理赔流程
- 多租户、权限体系、坐席工作台完整 UI（只做交接包 + 极简待处理列表）
- 语音、图片理解、多模态
- 训练/微调模型（只用现成模型 + prompt + 检索）
- 高并发与水平扩展（单机 + 弱网约束，不做容量证明）

## 与「公司业务」的边界

参考过一套线上 AI 客服系统的架构（已匿名化记录在 `docs/design-notes/reference-system.md`）。
**只借鉴形状，不复制实现**：代码全部重写、表结构重设计、命名体系自建、演示数据虚构。
任何带内部系统名/包名的原始材料都不进仓库。
